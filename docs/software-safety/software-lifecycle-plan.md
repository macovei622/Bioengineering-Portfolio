# Software Lifecycle Plan

## Status

This is a lightweight plan for maintaining the educational Python prototypes
in this repository. It is informed by lifecycle concepts in IEC 62304. It is
not a claim of IEC 62304 compliance, a complete medical-device software
lifecycle process, or a software safety-class assignment.

No medical-device software safety class has been assigned. The repository
software is not intended to perform a medical-device function. If an intended
use changes, classification and lifecycle activities must be determined by
the responsible organization under applicable requirements before that use.

## Software items and architecture

### Project 1

- `emg_pipeline.py`: CSV-part streaming, validation, exercise filtering,
  segmentation, feature extraction, grouped holdout, model training,
  evaluation, artifact serialization, plotting, and streaming example.
- `test_emg_pipeline.py`: focused automated tests for these functions and
  behaviors.
- External packages: NumPy, pandas, scikit-learn, Matplotlib, and joblib (see
  `requirements-python.txt`).
- Data: NinaPro DB1 CSV or its ordered parts. Input data are not generated by
  the software.

### Project 3

- `scaffold_diffusion.py`: geometry masks, Jacobi finite-difference solver,
  threshold analysis, mesh study, channel-grid search, and plotting.
- `test_scaffold_diffusion.py`: focused tests for masks, solver behavior,
  metrics, mesh study, and geometry ranking.
- External packages: NumPy and Matplotlib (also listed in
  `requirements-python.txt`).

## Lifecycle activities

For each change:

1. **Plan:** state the purpose, affected project and software items, expected
   behavior, and any change to intended use or assumptions.
2. **Specify:** update the relevant requirements and trace links before or
   alongside implementation.
3. **Design:** keep interfaces and numerical/model assumptions explicit;
   identify dependencies and failure behavior.
4. **Implement:** use version-controlled source, review changes, and avoid
   silent fallback behavior for invalid inputs or failed calculations.
5. **Verify:** run focused tests, relevant project tests, static/compile checks
   as appropriate, and record results in the verification report.
6. **Review risk:** update the risk register if a change affects outputs,
   assumptions, dependencies, intended use, or risk controls.
7. **Release:** record the commit, environment, input-data identity, model
   artifact identity when applicable, and known limitations.
8. **Maintain:** triage defects, assess impacts, fix or document them, and
   repeat affected verification after changes.

## Requirements and design traceability

Requirements use stable identifiers in
[requirements-traceability.md](./requirements-traceability.md). Each
requirement links to implementation and verification evidence where available.
Unverified requirements are explicitly marked; a missing link is not considered
successful verification.

## Verification and validation distinction

- **Verification:** whether the implemented software satisfies specified
  software requirements, e.g. window lengths, group boundaries, equations,
  and reported metrics.
- **Validation:** whether the software and its outputs satisfy a defined
  user need in the intended real-world context.

The existing unit tests provide limited verification. No clinical,
experimental-biological, user, usability, system-integration, or deployment
validation has been performed.

## Problem resolution

For a defect or unexpected result, record:

- a unique issue identifier and affected version;
- the observed behavior and steps/data required to reproduce it;
- severity and affected requirements or risk controls;
- root cause and corrective change;
- regression tests and review evidence;
- closure decision and release containing the correction.

Issues that may affect reported results, model behavior, or a documented risk
control remain open until evaluated; they must not be hidden by changing only
the report or plot.

## Release gate for this educational repository

A tagged educational release should at minimum have:

- a clean, reviewed source revision;
- relevant automated tests passing;
- dependency and data-source instructions;
- generated outputs clearly distinguished from source evidence;
- updated limitations, risk records, and trace links;
- no unsupported claim of medical-device conformity or clinical performance.

These gates are repository practices, not a substitute for a regulated
organization's quality management system.
